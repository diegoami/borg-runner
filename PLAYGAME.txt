== YOUR OWN WORKTREE, YOUR OWN BRANCH ==

You play in a worktree of the repository, not in the main checkout, so a run
never shares a working tree with another run or with maintainer work, and
what you write lands on a branch of its own. From
/home/diego/projects/borg-runner:

    git worktree add ../{RUNNAME} -b run/{RUNNAME}
    cd ../{RUNNAME}
    bash scripts/setup.sh
    uv venv .venv && uv pip install -e '.[test]' --python .venv/bin/python
    .venv/bin/python -m borg_runner build

The first build takes a few minutes; it is the price of isolation, paid once.
Everything after this happens in the worktree: every path in this prompt is
relative to it, and .venv/bin/python is its own. Your run cannot disturb
another run or be disturbed: each one owns its worktree, branch, run
directory, game process, seed, character and notebook. If the name is taken
by a live run the tool refuses and names the run holding it; pick another.

**And your own agent directory, agents/{AGENT}/.** Earlier sessions of your

    .venv/bin/python -m borg_runner playbook --family {AGENT} --class <CLASS>

    agents/{AGENT}/COMMON.md    everything your family has learned
    agents/{AGENT}/<CLASS>.md   the part that is only true of your class,
                                when your family has played one

**If a page of yours is missing, that command points you at another family's
page for the same class** - the same game, the same class, a different player.
Read it: knowledge is not private here. Say in your first note that you
borrowed it, and when you stop write your own page, naming what you took and
whether it held. You never edit theirs, and their numbers are theirs. If no
family has written about your class at all, you are the first and the page is
yours.

Weigh them by what is behind them: a FACT or an OBSERVED line is the game or
many runs, your playbook is one family's experience, a POLICY line is advice
nobody has settled. Where your playbook contradicts an OBSERVED line, follow
the OBSERVED line and say in your write-up which one held.

Everything else in the repository is lookup. An OBSERVED line on the page
names the runs that saw it as `run#ask`: `knowledge/<run>.md` is that run's own
notebook and `records/<run>/` its decisions and its replay, so you can see the
screen a claim came from. `manuals/INSTRUCTIONS_2.md` is depth 5 to 20, where
no run has been. Go to any of them for a number or a page, not before.

The manuals themselves are **not** in git: `scripts/setup.sh` clones them at
the commits `pins.json` names, so the text is the same text for every run.

    vendor/angband/lib/gamedata/*.txt  its data: every object, monster, class,

Do not read other runs' decisions or write-ups for your own seed - general

Your first note must say which files you actually opened, your own playbook

== START ==

    .venv/bin/python -m borg_runner play --seed {SEED} --name {RUNNAME}

If you were given a race or a class, add them, and they are recorded as a
deliberate choice rather than a draw:

    .venv/bin/python -m borg_runner play --seed {SEED} --name {RUNNAME} \
        --race {RACE} --class {CLASS}
    .venv/bin/python -m borg_runner wait --run runs/{RUNNAME}

Do not pass --notebook. Inherited knowledge belongs in the reading; your
notebook holds only what you find.

The game runs on by itself between your calls, waiting for the next key file,
and it is started in a session of its own so that it survives whatever
harness you are. If `wait` ever says the run has exited after you have only
just started it, say so rather than starting over: that is a bug worth
reporting, not something to work around.

== WHEN BIRTH ENDS, YOU ARE STANDING ON THE WAY DOWN ==

The town has one down staircase and **the game puts you on it**: `>` takes
you to depth 1 before you have walked anywhere. FACT,
`src/gen-cave.c town_gen_layout()` sets the staircase on the player's own
square and then places the player there; the status line says `Down
staircase` on your first screen, and `l` on your own square says it too.

Runs keep missing it. The tile under `@` is never drawn - the map draws you,
not the terrain you are standing on - so a player scanning for a `>` glyph
sees none and goes looking. Three runs raised this in their own notes, and the
one run that died at depth 0 never left the town at all.

So: shop first if you mean to - the stores are the digits `1`-`8` on the map,
and `M` draws the whole town with every door in it - then **`l>g`** walks you
back to the staircase the game already remembers, and `> ` takes it. The same
holds one level down: you arrive on an **up** staircase, which is your way out
of a level that will not give you anything, and `< ` then `> ` is a fresh
level of the same depth.

== PLAY: ONE CALL PER DECISION ==

    .venv/bin/python -m borg_runner answer <n> '<keys>' --run runs/{RUNNAME} \
        --reason "one line, your own words" \
        --note "a trick worth keeping, with the evidence that taught it"

`answer` sends the keys and prints the next screen, so after the first `wait`
it is one call per decision. `--note` appends to your notebook, which is
printed back to you with every later screen and given to whoever plays next;
nothing here ever writes to it or corrects it.

Keys: every character you send is a key the game receives. Four escapes exist
for keys that cannot be typed: \n Enter, \e Escape, \t Tab, \\ a backslash.
Several keys in one answer are usually right.

== TOOLS: THERE ARE SOME ALREADY, AND YOURS CAN BE KEPT ==

    .venv/bin/python -m borg_runner tools

lists the shared screen tools in `tools/screen/`, which earlier runs wrote and
which you may use as they are. They read a screen dump and print; none of them
presses a key:

    explore.py  where the level is still dark and the keys to send the game
              at it. Press `M` first and give it that screen: `M` draws the
              whole *remembered* level in one ask, and if a `>` is in it the
              tool tells you to use `l>g` rather than any code
    look.py   everything the screen has drawn, nearest first, with the offset
              from `@` in the game's own form (`3 S, 2 E`)
    aim.py    a place on the screen -> the keys that make *the game* walk
              there (`*`, cursor digits, `g`)
    map.py    the panel with coordinate rulers, and a local route over tiles
              that are drawn walkable
    diff.py   what changed between two screens - and whether anything did,
              which is how you catch a key that did nothing
    screen.py the reader the others use, if you write your own

They take `runs/{RUNNAME}/ask/screen-<n>.txt` directly:

    python3 tools/screen/look.py runs/{RUNNAME}/ask/screen-42.txt --map

**You may write your own** - a parser, a router, anything that reads the
screen. Two conditions, and then one thing to do at the end.

**Put yours in runs/{RUNNAME}/tools/ and say so in your first note.** They are
archived with the run, because a run played with a pathfinder you wrote is
measuring you *and your code*, and a reader a month later cannot tell the two
apart unless the code is there.

**Check the game first.** The game already does more than it looks: `l` then
`x` then `g` walks you to the nearest unexplored edge, `l` then `>` then `g`
to a known down staircase, and an aimed cursor plus `g` walks 17 to 44 tiles
in one ask through ground you have never seen. A tool that reimplements what
the game offers costs you the chance to find that out, and what you then write
in your notebook is about your tool instead of about Angband. One run spent
148 asks driving its own 143-line search and never tried the game's.

**When you stop, keep what was worth writing:**

    .venv/bin/python -m borg_runner tools --adopt runs/{RUNNAME}/tools/x.py \
        --from {RUNNAME}

That copies it into `tools/screen/` with a header naming your run, so the next
run starts with it instead of writing it again. Your own copy stays exactly as
you played it. `tools --check` must pass: a shared tool parses, says where it
came from, and does not import `borg_runner`.

== THE TIP THAT MATTERS MOST ==

`lxg` explores, `l>g` walks to a known down staircase, `l<g` back up. Send
each alone in its ask - any key after `g` cuts the walk to one step. That is
the game's own pathfinding, it is how the only deliberate descent in any run
happened, and it is in `manuals/INSTRUCTIONS.md` under "The one thing to take
from this page". No run has ever found a staircase by walking.

== RULES ==

- Your character is drawn unless you were given one. **Given neither a race
  nor a class, press * at the race menu and * at the class menu**, then read
  your class's block in INSTRUCTIONS section 9.
  Given a race or a class, **read its letter off the screen** and press that:
  the menu's letters skip h, j, k and l, so the fifth row is `e` but the
  eighth is `i` - counting rows will give you the wrong character. Press the
  letter, check the cursor moved to that row, then Enter. For whichever of
  the two you were not given, press *.
  The record keeps what the game actually produced and compares it with what
  you were asked for, so a mis-read menu shows up afterwards as
  `born_as_asked: false` rather than as a quietly different experiment.
- Take the easy option at birth: at the stat screen press a (point-based) then
  Enter to accept the allocation the game has filled in. Do not move points.
- Read the top line of the screen first. It is the game's message line and it
  usually says why your last key did nothing ("I see no up staircase here").
  A -more- there means a message is waiting and any key clears it.
- The header of each screen says `cursor at x,y`. In a menu that is the
  highlighted row, which the characters cannot show you.
- Change no setting, no option and no file outside your run directory.
- You may not call anything a defect. If you think a player could do better,
  say what would settle it.
- Aim for about 150 decisions unless you are told otherwise, then stop.
- **Depth is recorded, not scored.** Every run here has chased the down
  staircase as if it were the point, and two died at character level 1 doing
  it. Exploring the level you are on, levelling, going back to town for
  armour - the shops restock daily - and descending when you can pay for it is
  a plan, and so is deciding not to descend at all. Say in your report what
  you were buying with the asks you spent.
- **An unknown scroll or potion is a pool of kinds, not the one you want.**
  What it can be is fixed by the depth you found it at: on depth 1 or 2 the
  only unknown kinds in the game are scrolls and potions, and Magic Mapping
  is not among them. Section 6b of INSTRUCTIONS.md gives both pools with
  their odds and says how a kind becomes known - use it, buy one, or **give
  it to the store that buys that type**, which pays 0 gold with selling off
  and still identifies the kind for the rest of the game. That is the only
  way to learn something you dare not read, and it is worth a town trip.
- **Constitution sets how fast you may dive.** Read `CON` off `C`: it adds or
  subtracts hit points on *every* level, so two characters of one class can
  differ by ten, and a Mage, Necromancer, Rogue or Ranger is usually below
  zero on it. The rule is a pace, not a ban - gate each descent on the worst
  round of the depth you are entering (14 at depth 2 or shallower) and take
  more levels between descents when your constitution is low. "Constitution
  sets how fast you may dive" in manuals/INSTRUCTIONS.md has the table, the
  shopping list and the three deaths here, none of which was a big hit.
- **Levelling has a price list, and section 1 of INSTRUCTIONS.md is it.** What
  each character level costs, what a kill pays once your own level divides it,
  and what pays nothing at all - stairs, walking, resting, shopping,
  detection - are all there with the game's numbers. Read it before you decide
  what this run is for: it is the difference between deciding to level up and
  knowing what the fifth level actually costs in kills.
- **You never need to know where you are on the level.** A level you leave is
  regenerated, so no map of it has a second use, and both staircases are
  exits: `< ` then `> ` gives a fresh level of the same depth in two or three
  asks. When a level will not give you a staircase, leave it - this is not a
  game of persistent floors, and nothing here asks you to return to a place.

== WHEN YOU STOP: WRITE IT UP FIRST ==

**Write the report before you report to whoever started you.** Three of the
first ten runs here reported to their caller and wrote no file, so what they
found lived in a conversation and not in this repository - including the run
that reached depth 7. `archive` now says when a run wrote nothing, and the
table has a column for it, but the file is yours to write.

Write runs/{RUNNAME}/REPORT.md: what happened (depth, character level,
how it ended, decisions, turns; if you died, what killed you and the last
three decisions before it), the decisions you would take back, where the
reading was wrong or not enough, what you could not see or could not do, and
your leads - each with the evidence and what would settle it.

A broken run honestly reported is a result. A tidy story is not.

== THEN WRITE BACK TO agents/{AGENT}/ ==

Still before the commands. Your report is about this run and is read by
whoever reads this repository; your agent directory is read by the next
session of {AGENT} before its first keypress, which is the only place your
experience can change how your own model plays.

Update agents/{AGENT}/COMMON.md, and agents/{AGENT}/<CLASS>.md when your
class has one or has earned one. Three rules:

- **Fold it in, do not append a log.** A page a session cannot read whole is
  a page it will skim. If something you were told turned out to be wrong,
  correct that line rather than contradicting it further down.
- **Name the run every claim came from**, so a reader can check it against
  the record: `{RUNNAME}` is yours.
- **Keep it yours.** What belongs there is what you measured, what cost you
  asks and what you got wrong - not the manual restated. A general claim that
  any player should have belongs in your notebook, where `keep` promotes it
  into `knowledge/`.

**Append - do not rewrite.** Several runs of one family play at once, each
in its own worktree on its own branch, and the branches are merged afterwards
with merge=union: two appended sections both survive a merge, but two
whole-file rewrites of the same page make a tangle no merge can tidy. To add
your part without touching anyone else's:

    .venv/bin/python -m borg_runner playbook --family {AGENT} \
        --append - --from {RUNNAME} <<'MD'
    ## What I measured

    ... your lines, with the asks they came from ...
    MD

It takes a lock, re-reads the file inside it, and adds your section under a
heading of its own, so two runs that finish in the same second both survive.
Rewriting the body - folding the sections into the page - is work for a
session with nothing playing, not for you.

If your family has no COMMON.md yet, start one:

    .venv/bin/python -m borg_runner playbook --family {AGENT} --start {RUNNAME}

`archive` says afterwards whether you wrote back or not.

Then run all five, in order. The first three are about your run; the last
two publish it on your branch.

    .venv/bin/python -m borg_runner record --run runs/{RUNNAME} \
        --tokens <total> --tool-calls <total> \
        --played-by <session|codex|opencode|other> \
        --model <provider>/<exact model version> \
        --playbook {AGENT}

    .venv/bin/python -m borg_runner stop --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner keep --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner archive --run runs/{RUNNAME}
    git add records/{RUNNAME} knowledge/{RUNNAME}.md agents/{AGENT} && \
        git commit -m "{RUNNAME}: <depth, level, how it ended>" && \
        git push -u origin run/{RUNNAME}

Then check your own work, and say what it printed when you report back:

    .venv/bin/python -m borg_runner audit --run {RUNNAME}

It reads the archive and says whether everything a finished run should leave
is there: the files, the model and the family in the record, the promoted
notebook, your section in the playbook, the dashboard row, and whether git
has it. A `MISS` names the command that was skipped. Three of the first
eleven runs here left something out and nobody noticed until days later.

What each does:

- **stop** asks the game to save and quit. Nothing else does: when you stop
  answering, the game sits waiting for the next key for ever. A lingering
  game holds its character's savefile, which blocks anyone continuing your
  run, and it is the one step that is easy to forget because the run looks
  finished to you.

- **record** writes the run record: the seed, the build, the character the
  game drew, its level, its gold, the game's own valuation of what it
  carries, whether it died and to what. Leave the tokens and tool calls off
  rather than guessing. `--model` must name the provider and the exact
  version, e.g. `openai/gpt-5.6-luna`; a bare family name is refused, because
  two runs of the same family months apart are not the same experiment.
- **keep** promotes the notes *you* added into `knowledge/`, with the seed and
  build they came from. Notes you were handed are not promoted, so an
  inherited line is never counted as a second sighting.
- **archive** keeps the run in git: its keys, its decisions, its notes, its
  tools if you wrote any - and **generates its replay page**, which is how
  anyone watches your game back, screen by screen.
- **the commit** puts your run on its branch. You do not merge it and you do
  not rebuild the dashboard: both happen on the main checkout after the runs
  that are playing have finished, so two runs never race for the same files.
  The dashboard is served at <https://diegoami.github.io/borg-runner/> once
  your branch is merged and the overview is rebuilt there. Name your branch
  when you report back.

If the replay page itself ever needs rebuilding for every run - after someone
changes it - that is `borg_runner report --all`, not something a run does.
