Carry on a game of Angband 4.2.6 that an earlier run stopped playing.

Substitute the placeholders. If you were given only the run to continue,
**leave {RUNNAME} out of the start command**: `carry-on` names the run itself,
as the next generation of the character.

A lineage is `<base>.<generation>`: a character born as `rogue-1` continues as
`rogue-1.2`, then `rogue-1.3`. The base names the character for its whole
life, the number says which life this is, and the runs sort next to each
other. Two runs here end in `-again` and predate that; continuing one gives
`.3`, because `-again` was generation 2.

    {FROM}      the run to continue, e.g. sonnet-2-again
    {RUNNAME}   the new run, e.g. sonnet-2-again-2

Work from /home/diego/projects/borg-runner and use .venv/bin/python. Your run
will not disturb any other: each one owns its directory, game process,
character and notebook.

== WHY THIS IS A NEW RUN AND NOT A RESTART ==

A stopped game cannot be reopened. The frontend numbers its asks from one each
process, so a second process would overwrite the first one's questions, and a
game resumed from a savefile is no longer reproduced by its seed and its keys.

So `carry-on` replays the old keys into a fresh run - which is exact - and
leaves the game waiting at the next ask, with the old notebook already in
place. Your run's `input.txt` ends up being the whole history, the old keys
and yours, so it replays from its seed like any other.

== START ==

    .venv/bin/python -m borg_runner carry-on --run runs/{FROM}

It prints the name it chose - the next generation of the character - and that
is your {RUNNAME} for every command below. Pass `--name` only if you were
given one.

It prints `waiting_at_ask` and the turn. That ask number is where you begin -
**not 1**. It also prints `identical`: true means the replay reproduced the
old game exactly. If it is false, read runs/{RUNNAME}/replay.json before
playing: a difference only at ask 1 is the known build-id change in older
recordings and is harmless, anything else means this is not the same game and
you should say so rather than play on.

    .venv/bin/python -m borg_runner wait --run runs/{RUNNAME}

== READ ==

    manuals/INSTRUCTIONS.md   the manuals distilled. Section 9 has a block per
                              class - **read the block for the character you
                              have inherited**, which the screen's sidebar and
                              `C` will tell you.
    knowledge/NOTES.md        what earlier runs found. Where these two
                              disagree, NOTES wins.
**Your own history, which no manual contains.** This character has lived
before, perhaps more than once. Run

    .venv/bin/python -m borg_runner history --run runs/{RUNNAME}

and **read every write-up it lists, oldest first**. The same chain is in
`runs/{RUNNAME}/history.json`. Those are your own past lives: where the
character has been, what it tried, what it would have done differently. Your
notebook carries what it *learned*; the write-ups carry what it *did*, and
nothing else records that.

You may read these. A different run's transcript of your seed is still a
solution key and is still out of bounds - the distinction is that this is
your own history.

Your notebook already contains the notes of every run in that chain, and they
are printed back to you with every screen. Do not restate them. Add only
what is new, or what contradicts them - and when something they claim turns
out to be wrong, say so with the evidence.

Your first note must say which files you actually opened, **including which
of your own write-ups**.

Do not read a *different* run's decisions or write-up for this seed. The run
you continue is your own past; another run's transcript of the same dungeon is
a solution key.

== PLAY: ONE CALL PER DECISION ==

    .venv/bin/python -m borg_runner answer <n> '<keys>' --run runs/{RUNNAME} \
        --reason "one line" --note "something new, with its evidence"

`answer` prints the next screen. Several keys in one answer are usually right;
the escapes are \n Enter, \e Escape, \t Tab, \\ a backslash.

== WHAT IS DIFFERENT FROM A FRESH RUN ==

- There is no birth. Your character exists, with its level, its gear and its
  wounds. Press `i`, `e` and `C` early: nothing here remembers what it carries
  for you, and the run before you may have spent things.
- You inherit its position, which may be bad. Read the top line of the screen
  and the status line before you move. The run before you may have left you
  slowed, confused, out of escapes, or next to something it was losing to.
- Rest before you descend, and know what you are carrying before you fight.

== RULES ==

- Change no setting, no option and no file outside your run directory.
- You may not call anything a defect. If a player could do better, say what
  would settle it.
- Aim for about 150 decisions unless told otherwise, then stop.

== WHEN YOU STOP: RECORD IT AND UPDATE THE DASHBOARD ==

Run all six, in order. The first three are about your run; the last two
publish it, and they are what makes your run visible to anyone else.

    .venv/bin/python -m borg_runner record --run runs/{RUNNAME} \
        --tokens <total> --tool-calls <total> \
        --played-by <session|codex|opencode|other> \
        --model <provider>/<exact model version>

    .venv/bin/python -m borg_runner stop --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner keep --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner archive --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner overview
    git add records knowledge index.html && \
        git commit -m "{RUNNAME}: <depth, level, how it ended>" && \
        git pull --rebase -q && git push -q

What each does:

- **stop** asks the game to save and quit. Nothing else does: when you stop
  answering, the game sits waiting for the next key for ever. A lingering
  game holds its character's savefile, which blocks anyone continuing your
  run, and it is the one step that is easy to forget because the run looks
  finished to you.

- **record** writes the run record: the seed, the build, the character the
  game drew, its level, its gold, the game's own valuation of what it
  carries, whether it died and to what. Leave the tokens and tool calls off
  rather than guessing. `--model` must name the provider and the exact
  version, e.g. `openai/gpt-5.6-luna`; a bare family name is refused, because
  two runs of the same family months apart are not the same experiment.
- **keep** promotes the notes *you* added into `knowledge/`, with the seed and
  build they came from. Notes you were handed are not promoted, so an
  inherited line is never counted as a second sighting.
- **archive** keeps the run in git: its keys, its decisions, its notes, its
  tools if you wrote any - and **generates its replay page**, which is how
  anyone watches your game back, screen by screen.
- **overview** rebuilds the dashboard: `records/OVERVIEW.md`, `index.html` and
  `records/overview.html`, all three from the records.
- **the commit** publishes it. The dashboard is served at
  <https://diegoami.github.io/borg-runner/>, so until you push, your run is
  not there. Pull with a rebase first: other runs may have finished while you
  played, and only `records/`, `knowledge/` and the dashboard files are yours
  to add.

If the replay page itself ever needs rebuilding for every run - after someone
changes it - that is `borg_runner report --all`, not something a run does.

**Write the report before you report to whoever started you.** Three of the
first ten runs here reported to their caller and wrote no file, so what they
found lived in a conversation and not in this repository - including the run
that reached depth 7. `archive` now says when a run wrote nothing, and the
table has a column for it, but the file is yours to write.

Then write runs/{RUNNAME}/REPORT.md: where you took the character and where
you left it, the decisions you would take back, where the reading was wrong or
not enough, what you could not see or do, and your leads with what would
settle each.

A broken run honestly reported is a result. A tidy story is not.
