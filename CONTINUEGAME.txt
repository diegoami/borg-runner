Carry on a game of Angband 4.2.6 that an earlier run stopped playing.

Substitute the placeholders. If you were given only the run to continue,
**leave {RUNNAME} out of the start command**: `carry-on` names the run itself,
as the next generation of the character.

A lineage is `<base>.<generation>`: a character born as `rogue-1` continues as
`rogue-1.2`, then `rogue-1.3`. The base names the character for its whole
life, the number says which life this is, and the runs sort next to each
other. Two runs here end in `-again` and predate that; continuing one gives
`.3`, because `-again` was generation 2.

    {FROM}      the run to continue, e.g. sonnet-2-again
    {RUNNAME}   the new run, e.g. sonnet-2-again-2
    {AGENT}     which agent you are, as a model family: minimax, sonnet,
                codex, qwen, glm. It names your own directory of notes,
                agents/{AGENT}/, which you read before you play and write
                back to before you stop. It is yours even when the character
                you inherit was played by another family

Work from /home/diego/projects/borg-runner and use .venv/bin/python. Your run
will not disturb any other: each one owns its directory, game process,
character and notebook.

== WHY THIS IS A NEW RUN AND NOT A RESTART ==

A stopped game cannot be reopened. The frontend numbers its asks from one each
process, so a second process would overwrite the first one's questions, and a
game resumed from a savefile is no longer reproduced by its seed and its keys.

So `carry-on` replays the old keys into a fresh run - which is exact - and
leaves the game waiting at the next ask, with the old notebook already in
place. Your run's `input.txt` ends up being the whole history, the old keys
and yours, so it replays from its seed like any other.

== START ==

    .venv/bin/python -m borg_runner carry-on --run runs/{FROM}

It prints the name it chose - the next generation of the character - and that
is your {RUNNAME} for every command below. Pass `--name` only if you were
given one.

It prints `waiting_at_ask` and the turn. That ask number is where you begin -
**not 1**. It also prints `identical`: true means the replay reproduced the
old game exactly. If it is false, read runs/{RUNNAME}/replay.json before
playing: a difference only at ask 1 is the known build-id change in older
recordings and is harmless, anything else means this is not the same game and
you should say so rather than play on.

    .venv/bin/python -m borg_runner wait --run runs/{RUNNAME}

== READ ==

    manuals/INSTRUCTIONS.md   the manuals distilled, with what earlier runs
                              found folded in and labelled: FACT from the
                              game's data, OBSERVED from runs (with how many
                              saw it), POLICY to be tested, UNTESTED by
                              anyone. Section 9 has a block per class -
                              **read the block for the character you have
                              inherited**, which the screen's sidebar and `C`
                              will tell you.

**Your own agent directory, agents/{AGENT}/.** Earlier sessions of your own
model family wrote it for the next one, which is you: what they measured, what
cost them asks, what they got wrong. This prints which pages exist, for your
family and the class you have inherited:

    .venv/bin/python -m borg_runner playbook --family {AGENT} --class <CLASS>

**If a page of yours is missing, that command points you at another family's
page for the same class**, which is worth opening anyway when you inherit a
character another family played: the same game, the same class, a different
player. Read it, say in your first note that you borrowed it, and write your
own when you stop - naming what you took and whether it held. You never edit
theirs. If no family has written about your class at all, you are the first.

Weigh them by what is behind them: a FACT or an OBSERVED
line is the game or many runs, a playbook is one family's experience, a POLICY
line is advice nobody has settled. An OBSERVED line names the runs that saw
it as `run#ask`, and `knowledge/<run>.md` and `records/<run>/` are that run's
notebook and decisions - including, where the run is one of your own past
lives, yours.

The manuals themselves are **not** in git: `scripts/setup.sh` clones them at
the commits `pins.json` names, so the text is the same text for every run.

    vendor/angband/docs/*.rst          the game's own manual: guide, playing,
                                       command, attack, birth, dungeon
    vendor/angband/lib/gamedata/*.txt  its data: every object, monster, class,
                                       store and trap, with the real numbers
    vendor/angband/src/*.c             what the game actually does
    vendor/strategy-manual             seventeen chapters and ten appendices,
                                       read through git rather than opened:
                                         cd vendor/strategy-manual
                                         git cat-file -p HEAD:docs/c-manual/README.md
                                         git cat-file -p HEAD:docs/c-manual/15-notes-for-the-borg.md

INSTRUCTIONS.md is those two cut to what a player uses, and every line of it
says which of them it came from - so going to a source is a lookup for one
number or one page, not a second reading. The appendices are tables: grep them
when you meet something, never read them through.

**Your own history, which no manual contains.** This character has lived
before, perhaps more than once. Run

    .venv/bin/python -m borg_runner history --run runs/{RUNNAME}

and **read every write-up it lists, oldest first**. The same chain is in
`runs/{RUNNAME}/history.json`. Those are your own past lives: where the
character has been, what it tried, what it would have done differently. Your
notebook carries what it *learned*; the write-ups carry what it *did*, and
nothing else records that.

You may read these. A different run's transcript of your seed is still a
solution key and is still out of bounds - the distinction is that this is
your own history.

Your notebook already contains the notes of every run in that chain, and they
are printed back to you with every screen. Do not restate them. Add only
what is new, or what contradicts them - and when something they claim turns
out to be wrong, say so with the evidence.

Your first note must say which files you actually opened, **including which
of your own write-ups** and your own playbook.

Do not read a *different* run's decisions or write-up for this seed. The run
you continue is your own past; another run's transcript of the same dungeon is
a solution key.

== PLAY: ONE CALL PER DECISION ==

    .venv/bin/python -m borg_runner answer <n> '<keys>' --run runs/{RUNNAME} \
        --reason "one line" --note "something new, with its evidence"

`answer` prints the next screen. Several keys in one answer are usually right;
the escapes are \n Enter, \e Escape, \t Tab, \\ a backslash.

== TOOLS: THERE ARE SOME ALREADY, AND YOURS CAN BE KEPT ==

    .venv/bin/python -m borg_runner tools

lists the shared screen tools in `tools/screen/` - `explore.py` (where the
level is still dark; press `M` and give it that screen), `look.py` (what the
screen has drawn, with offsets from `@`), `aim.py` (a place -> the keys that
make the *game* walk there), `map.py` (the panel with rulers and a local
route), `diff.py` (what changed, and whether anything did), `screen.py` (the
reader).
They take `runs/{RUNNAME}/ask/screen-<n>.txt` directly and press no keys.

If you inherited tools from your own earlier life they are in
`runs/{RUNNAME}/tools/`, copied forward with the run. You may write more;
check the game's own commands first, because an aimed cursor plus `g` walks 17
to 44 tiles in one ask and no code of yours will beat it. When you stop, keep
what was worth writing:

    .venv/bin/python -m borg_runner tools --adopt runs/{RUNNAME}/tools/x.py \
        --from {RUNNAME}

== WHAT IS DIFFERENT FROM A FRESH RUN ==

- There is no birth. Your character exists, with its level, its gear and its
  wounds. Press `i`, `e` and `C` early: nothing here remembers what it carries
  for you, and the run before you may have spent things.
- **If you were left in the town, the staircase down is under you or one
  `l>g` away.** The town has one, the game remembers it, and the tile under
  `@` is never drawn - so read the status line rather than looking for a `>`
  on the map (`src/gen-cave.c town_gen_layout()`; three runs raised this in
  their own notes).
- You inherit its position, which may be bad. Read the top line of the screen
  and the status line before you move. The run before you may have left you
  slowed, confused, out of escapes, or next to something it was losing to.
- Rest before you descend, and know what you are carrying before you fight.

== RULES ==

- Change no setting, no option and no file outside your run directory.
- You may not call anything a defect. If a player could do better, say what
  would settle it.
- Aim for about 150 decisions unless told otherwise, then stop.
- **Depth is recorded, not scored.** Every run here has chased the down
  staircase as if it were the point, and two died at character level 1 doing
  it. Exploring the level you are on, levelling, going back to town for
  armour - the shops restock daily - and descending when you can pay for it is
  a plan, and so is deciding not to descend at all. Say in your report what
  you were buying with the asks you spent.
- **Levelling has a price list, and section 1 of INSTRUCTIONS.md is it.** What
  each character level costs, what a kill pays once your own level divides it,
  and what pays nothing at all - stairs, walking, resting, shopping,
  detection - are all there with the game's numbers. Read it before you decide
  what this run is for: it is the difference between deciding to level up and
  knowing what the fifth level actually costs in kills.
- **You never need to know where you are on the level.** A level you leave is
  regenerated, so no map of it has a second use, and both staircases are
  exits: `< ` then `> ` gives a fresh level of the same depth in two or three
  asks. When a level will not give you a staircase, leave it - this is not a
  game of persistent floors, and nothing here asks you to return to a place.

== WHEN YOU STOP: WRITE IT UP FIRST ==

**Write the report before you report to whoever started you.** Three of the
first ten runs here reported to their caller and wrote no file, so what they
found lived in a conversation and not in this repository - including the run
that reached depth 7. `archive` now says when a run wrote nothing, and the
table has a column for it, but the file is yours to write.

Write runs/{RUNNAME}/REPORT.md: where you took the character and where
you left it, the decisions you would take back, where the reading was wrong or
not enough, what you could not see or do, and your leads with what would
settle each.

A broken run honestly reported is a result. A tidy story is not.

== THEN WRITE BACK TO agents/{AGENT}/ ==

Still before the commands. Your report is about this life of this character;
your agent directory is read by the next session of {AGENT} before its first
keypress, whatever character it gets, and that is the only place your
experience can change how your own model plays.

Update agents/{AGENT}/COMMON.md, and the page for the class you inherited
when it has one or has earned one. Three rules:

- **Fold it in, do not append a log.** A page a session cannot read whole is
  a page it will skim. A line that turned out to be wrong gets corrected
  where it stands, not contradicted further down - and you are the session
  best placed to do that, because you played on what it said.
- **Name the run every claim came from**: `{RUNNAME}` is yours.
- **Keep it yours.** What you measured, what cost you asks, what you got
  wrong. A claim any player should have belongs in your notebook instead,
  where `keep` promotes it into `knowledge/`.

**If any other run is playing, append - do not rewrite.** Several runs of one
family play here at once and they all write to these same pages, so the last
whole-file rewrite erases the others. `playbook --family {AGENT}` says how
many games are in progress. To add your part without touching anyone else's:

    .venv/bin/python -m borg_runner playbook --family {AGENT} \
        --append - --from {RUNNAME} <<'MD'
    ## What I measured

    ... your lines, with the asks they came from ...
    MD

It takes a lock, re-reads the file inside it, and adds your section under a
heading of its own, so two runs that finish in the same second both survive.
Rewriting the body - folding the sections into the page - is work for a
session with nothing playing, not for you.

If your family has no COMMON.md yet, start one:

    .venv/bin/python -m borg_runner playbook --family {AGENT} --start {RUNNAME}

`archive` says afterwards whether you wrote back or not.

Then run all six, in order. The first three are about your run; the last two
publish it, and they are what makes your run visible to anyone else.

    .venv/bin/python -m borg_runner record --run runs/{RUNNAME} \
        --tokens <total> --tool-calls <total> \
        --played-by <session|codex|opencode|other> \
        --model <provider>/<exact model version> \
        --playbook {AGENT}

    .venv/bin/python -m borg_runner stop --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner keep --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner archive --run runs/{RUNNAME}
    .venv/bin/python -m borg_runner overview
    git add records knowledge agents index.html && \
        git commit -m "{RUNNAME}: <depth, level, how it ended>" && \
        git pull --rebase -q && git push -q

Then check your own work, and say what it printed when you report back:

    .venv/bin/python -m borg_runner audit --run {RUNNAME}

It reads the archive and says whether everything a finished run should leave
is there: the files, the model and the family in the record, the promoted
notebook, your section in the playbook, the dashboard row, and whether git
has it. A `MISS` names the command that was skipped. Three of the first
eleven runs here left something out and nobody noticed until days later.

What each does:

- **stop** asks the game to save and quit. Nothing else does: when you stop
  answering, the game sits waiting for the next key for ever. A lingering
  game holds its character's savefile, which blocks anyone continuing your
  run, and it is the one step that is easy to forget because the run looks
  finished to you.

- **record** writes the run record: the seed, the build, the character the
  game drew, its level, its gold, the game's own valuation of what it
  carries, whether it died and to what. Leave the tokens and tool calls off
  rather than guessing. `--model` must name the provider and the exact
  version, e.g. `openai/gpt-5.6-luna`; a bare family name is refused, because
  two runs of the same family months apart are not the same experiment.
- **keep** promotes the notes *you* added into `knowledge/`, with the seed and
  build they came from. Notes you were handed are not promoted, so an
  inherited line is never counted as a second sighting.
- **archive** keeps the run in git: its keys, its decisions, its notes, its
  tools if you wrote any - and **generates its replay page**, which is how
  anyone watches your game back, screen by screen.
- **overview** rebuilds the dashboard: `records/OVERVIEW.md`, `index.html` and
  `records/overview.html`, all three from the records.
- **the commit** publishes it. The dashboard is served at
  <https://diegoami.github.io/borg-runner/>, so until you push, your run is
  not there. Pull with a rebase first: other runs may have finished while you
  played, and only `records/`, `knowledge/`, your own `agents/{AGENT}/` and
  the dashboard files are yours to add.

If the replay page itself ever needs rebuilding for every run - after someone
changes it - that is `borg_runner report --all`, not something a run does.
